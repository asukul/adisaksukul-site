Part 5 · TREC and the 2026 tracks · Chapter 26

Agents and skills in the 2026 track

In one sentence: a coding agent is a language model that reads files and runs commands toward a goal, a skill is a folder of instructions it loads when needed, and in 2026 the RAG track wrote its rules for both people and agents.

Why you should care

The 2026 shift said what changed. This chapter is about how to work in that world. An agent can build in an afternoon what took a team a week. It can also make a quiet mistake in a second and repeat it over 119 narratives. Your value moves from typing the code to setting the task and checking the result. The examples here are our own, including the errors.

Words you need

Agent
A system in which a language model decides its own next steps and which tools to use, over many steps.
Workflow
A system in which the steps are fixed in code and the model fills in each one. Most RAG pipelines in this book are workflows.
Skill
A folder with a file called SKILL.md and, if needed, reference files and scripts. The agent loads it when a task matches its description.
Context
Everything the model can see at one moment: instructions, files it has read, results of commands. It is limited.
Progressive disclosure
Showing the agent a short description first and the details only when it needs them.
Verification pass
A second, independent check of a result, done by a person, a program or another agent that did not produce it.
Audit
Comparing what was claimed with what the files show.

Core The idea

What a skill looks like

A skill is plain text in a folder. The top of SKILL.md has a name and a description. The agent reads only those two lines at first. If a task matches the description, it reads the rest, and then only the reference files it needs. This keeps the context small, which matters because a model with a crowded context makes more mistakes.

Read the rules in the right column again. Each one names a typical agent failure: reading too much, leaking a secret, making up an identifier. The guidelines skill says who it is talking to: “you, the agent or developer building, validating, or explaining a TREC RAG 2026 run”. The track's home page does the same. It tells an agent that was sent there to keep its context small and to stay inside the guidelines skill.

Three ways to share the work

  • The agent as assistant. You design the pipeline. The agent writes and runs the code for each stage. Most of our RAG work was done this way.
  • The agent as a stage. The pipeline is fixed, and an agent does one step in it, such as writing a report from supplied documents.
  • The agent as the system. The agent searches, reads, searches again and writes, with no fixed pipeline. One of the organizers' baselines worked this way.

What stays with the person

  1. The question. What are we trying to learn, and which two runs would show it?
  2. The rules. Which data may be used, and what must stay private.
  3. The decision. Which runs to send, and in what priority.
  4. Outside actions. Registering, signing forms, sending e-mail, publishing.
  5. The check. Reading enough of the output to know the summary is true.

How to supervise

An agent's report of its own work is a claim, not evidence. Three habits turn claims into evidence. Ask for files, not summaries: the run, the log and the exact prompt. Have a different checker verify the result, with the files and without the first agent's conclusion. And recompute numbers from the saved files with a small separate program.

How we did it at TREC 2026

On the submission forms that asked, we marked the runs as automatic and described the use of agents. A person registered the team, signed the agreements, chose the runs and their priorities, sent every e-mail, and approved anything that became public.

What surprised us

The errors were quiet, and every one was found by comparing with files. None of these stopped a program or printed a warning.
  • A default nobody chose. A script's default setting gave our two main RAG runs different document orders. The run description said otherwise (Chapter 22).
  • A setting dropped in silence. A generation script removed some settings after the model service rejected them, and wrote nothing to its log.
  • A description that was not true. Our RAGTIME notes said the writer saw the full text. The files showed the first 2,400 characters of each document, which cut about half of the documents.
  • Invented citations. Before upload, we found answers with made-up citation markers and four narratives with no references at all (Chapter 24).
  • A draft with wrong numbers. A first write-up of our Change Detection results gave the wrong cut-off for six of seven runs. An exact replay of the runs corrected it.
In one results page a checking pass ran 2,263 automatic checks and two failed. After the fixes, 2,588 ran and none failed. The lesson is not that agents are careless. It is that fluent text hides small errors from a reader, and only a comparison with the files finds them.

One more thing went wrong, and it was ours. The instructions given to the agents that wrote the nugget questions were not saved. We know what the agents produced and not exactly what they were told. A prompt is part of the method, so keep it with the run.

Try it

  1. Open the guidelines skill. Read only SKILL.md. Which reference file would you open to answer “how long may an answer be”?
  2. Give a coding agent the skill and one narrative. Ask for one valid RAG record for that narrative, with the log of what it did.
  3. Audit it. Does every cited ID appear in the documents the agent actually retrieved? Count the words with the track's rule.
  4. Ask a second agent, or a classmate, to check the record against the guidelines without seeing the first agent's summary.
  5. Write down one thing the first agent said that the files did not support, if there is one.

Check yourself

  1. What is the difference between a workflow and an agent?
  2. What is in a skill folder, and what does the agent read first?
  3. Why does the guidelines skill tell the agent to load only the files it needs?
  4. Name three things that stayed with a person in our entry.
  5. What do the five quiet errors in this chapter have in common?
Answers
  1. In a workflow the steps are fixed in code. An agent chooses its own steps and tools as it goes.
  2. A SKILL.md file with a name, a description and instructions, plus optional reference files and scripts. The agent first reads only the name and description.
  3. Context is limited, and a crowded context leads to more mistakes.
  4. Any three of: the research question, the data rules, the choice and priority of runs, registration and forms, e-mail, publishing, the final check.
  5. None raised an error. Each was found by comparing a claim with the saved files.

Go deeper

  • Write your own skill. Take one thing your team explains to every new member, such as how to validate a run. Put it in a folder with a twenty-line SKILL.md. Test whether an agent with the skill makes fewer mistakes than one without.
  • Agentic RAG. The organizers' agent baseline returned between 4 and 15 documents per narrative, where the BM25 baseline returned thousands. An agent that searches, reads and decides when to stop fits the “all and only” rule naturally. Chapter 10 has the trade.
  • Agents and blind data. In Auto-Judge, the policy on what may be looked at applies to your coding agent as well as to you. An agent that prints a file to the screen has “looked”. Plan what an agent is allowed to open before it starts.
  • Independent checkers. A checker that is handed the first agent's conclusion tends to agree with it. Give the checker the files and the question only.
  • Cost. Agents spend tokens on reading and re-reading. One of our Video QA runs used about 7 million tokens through agents, and another run with a different model and direct calls used 5.7 million input tokens. The two are not a fair comparison. Measure it for your own task.
  • Project idea. Give the same task to an agent three times. Compare the three logs. Which decisions differed, and did any of them change the output?
