Part 5 · TREC and the 2026 tracks · Chapter 25

The new corpus: NVIDIA ClimbMix-400b

In one sentence: ClimbMix-400b is a 400-billion-token collection of text that NVIDIA built for training language models, and in 2026 the RAG track used it as the place where every answer must be found.

Why you should care

A RAG system can only be as good as the collection behind it, and every collection has a character. This one is unusual in three ways. It was made to train models, not to be searched. Its documents are whole texts with no title and no web address. And it is far too large for most student teams to index, so you reach it through a search service. Each of these changes how you build.

Words you need

Corpus
The collection of documents a system searches. Plural: corpora.
Token
The unit a language model reads, roughly three quarters of an English word.
Pre-training data
The large body of text a language model learns from before any fine-tuning.
Shard
One file of a collection that has been split into many files.
Document ID
The name of one document. In ClimbMix it is the shard name and the row number, such as shard_01789_3390.
Hosted index
A search index that someone else runs and that you query over the network.
Baseline run
A run released by the organizers that any team may start from.
Evidence pool
The set of documents you collected for one question, before choosing which ones the writer will see.

Core The idea

Where it comes from

NVIDIA researchers started from two large public collections of web and educational text. They grouped the text by topic, scored it with two classifiers, one for advertisements and one for educational value, and removed the low-scoring material. The result of the search for a good mixture was a 1.2-trillion-token collection called ClimbLab and a smaller, 400-billion-token one called ClimbMix. The “400b” in the name is that token count.

The track uses a public copy of ClimbMix stored as 6,543 files of plain text, about 600 gigabytes in all. The copy has one column, the text. So the track defined the document ID itself: the file name and the row number. Its rules for rebuilding the collection are strict for that reason. Do not reshuffle, deduplicate, filter or reorder before you assign IDs, or your IDs will not match anyone else's.

Three things follow for a RAG builder.

  • Documents are long. In the part of the collection we stored, a document averaged about 18,000 characters, and nearly half reached the 24,000-character limit of our store. You must decide how much of each document the writer sees (Chapter 13).
  • There is no title or address. You cannot show the reader a source name, and you cannot use the title as a search field. A citation is an ID and nothing more.
  • The model may have seen it. This is training data. One of the track's stated goals is to align its test collection with what language models are trained on, because then we know what the model has seen. It makes a new question possible: does a model answer better from a document it met in training?

Reaching it without downloading it

The organizers run a search service. You ask for a personal token once, and then send two kinds of request: search an index with a query and a number of hits, or fetch one document by its ID. The search is BM25 over the text (Chapter 5). The query is treated as plain words. Special search syntax is not supported.

The service is shared by all teams, so it comes with manners, written into the track's skill:

  • Each worker has at most one request in flight. Send the next one when the last one has returned, not on a timer.
  • Around a dozen workers is acceptable. Use fewer if errors or slow replies appear.
  • When the service answers “too many requests”, wait as long as it says, or wait 1, 2, 4 seconds and so on, up to a minute.
  • Never print the token, paste it into a chat, or commit it to a repository.

The released baselines

You do not have to search at all to begin. The organizers released a BM25 run with 5,000 documents per narrative, and the top 1,000 again as a file that includes the full text of every document. They also released several reranked runs and one run made by a search agent, which returned only 4 to 15 documents per narrative. A team with one laptop can build a complete RAG entry from these files.

How we did it at TREC 2026

We never downloaded the collection. Every run started from the search service and the released baseline files.

The store let us run the experiment in our talk title. The first version of our answers saw exactly 500 characters of each document, about 8,300 words of evidence per narrative. The second saw up to 1,000 words of each of 100 documents, about 90,000 words per narrative (Chapter 13).

What surprised us

“OK” with nothing inside. Under load, the search service sometimes answered with a success code and an empty list of results. Nothing in the reply said that anything was wrong. A script that trusts the success code would record “no documents for this query” and move on, and a narrative would quietly lose part of its pool. Our script treats an empty list as a failure and asks again. The general rule: check the content of a reply, not only its status.

A second surprise came when we looked inside the store for this chapter. We found 432 groups of documents with exactly the same text under different IDs, covering 1,052 IDs. In a collection built by mixing sources, copies are to be expected, and the rule against deduplicating keeps them in. For a RAG system it means that two of your top ten documents may be one document. We did not remove copies from our evidence, and we have not measured near-copies.

Try it

  1. Open the released baseline file with full text. For one narrative, read the first three documents from start to end. How long are they? Where in each document is the useful part?
  2. Write three shorter queries for the same narrative by rule: the first sentence, the last sentence, and the ten rarest words.
  3. If you have a token, send the three queries with 100 hits each, one request at a time. If not, use any search library on the baseline file's documents.
  4. Fuse the lists and keep 100 documents. How many came from only one of the queries?
  5. Look for exact copies in your 100. Did you find any?

Check yourself

  1. What does “400b” in the name stand for?
  2. What was ClimbMix made for, and why does that matter for RAG research?
  3. How is a ClimbMix document ID formed, and why must nobody reorder the files first?
  4. State two of the service's pacing rules.
  5. Why should a script check for an empty result list even when the reply says success?
Answers
  1. 400 billion tokens.
  2. For training language models. A model under test may have seen the documents in training, which the track wants to study.
  3. The shard file name plus the row number. Reordering would give documents different IDs from the official ones, and runs could not be scored.
  4. Any two of: one request in flight per worker; about a dozen workers at most; wait when told “too many requests”; no fixed timer.
  5. Under load the service can return success with no results. Trusting it would silently drop documents from the pool.

Go deeper

  • Only BM25 is hosted. The service offers no dense index. A team that wants dense retrieval over the whole collection must build it, which is a large job. Reranking a deep BM25 pool, as we did, is the cheaper route, and it can never find a document that BM25 missed in all seven queries.
  • Seen in training. Design an experiment that separates “the model knows this” from “the model read this in the prompt”. One way is to ask the question with no documents at all and compare.
  • Whole documents and citations. A citation to an 18,000-character document is hard for a reader to check. Compare with RAGTIME, where a judge must find the support inside a news article (Chapter 19).
  • Quality filtering. The collection was filtered for educational value. What kinds of question will such a collection answer badly? Recent news and opinions are two guesses worth testing.
  • What we do not know. We could not confirm the total number of documents in the collection, or the average length over all of it. The figures in this chapter describe only the 109,388 documents we stored.
  • Project idea. Measure copies and near-copies in the top 100 of the BM25 baseline for all 119 narratives. Then remove them before generation and see whether nugget scores change.
