Part 2 · Finding the evidence · Chapter 8

Combining lists: fusion

In one sentence: when several searches each return a ranked list, fusion merges them into one list, and the simplest good way to do it uses only the positions of the documents.

Why you should care

No single search finds everything. A keyword search misses documents that use other words. An embedding search misses exact names and numbers. A long question can be searched in many ways, and each way finds a slightly different set. If you can merge the lists well, you keep the strengths of each search. Almost every modern RAG system has a fusion step, and in ours it is one line of arithmetic.

Words you need

Ranked list
The documents a search returns, best first. Position 1 is the top.
Rank
A document's position in one list: 1, 2, 3 and so on.
Fusion
Merging several ranked lists into one.
Reciprocal Rank Fusion (RRF)
A fusion method that gives each document 1 / (k + rank) points from every list it appears in, and adds the points up.
k
The constant in RRF. A larger k makes the top positions matter less. The usual value is 60.
Score fusion
Fusion that adds the searches' scores instead of using positions. CombSUM is the best-known kind.
Hybrid search
Keyword search and embedding search run together, then fused.
Pool
The set of candidate documents that goes on to the next step.

Core The idea

Suppose three friends each give you a ranked list of restaurants. You want one list. You could ask each friend for marks out of ten and add them up. But one friend gives everything a nine, and another never goes above six. Their marks are not on the same scale, so the generous friend decides the result.

Positions do not have this problem. “Second on my list” means the same thing for every friend. Reciprocal Rank Fusion uses only positions:

score(document) = sum over all lists of   1 / (k + rank in that list)
A document that is missing from a list gets nothing from that list. Sort by score, highest first.

With k = 60, first place in a list is worth 1/61, second place 1/62, and place 100 is worth 1/160. The points fall slowly. So one first place is worth less than two decent places, and a document that several searches agree on rises to the top.

Three things to notice:

  • d1 wins without being first twice. It is in all three lists, near the top each time. Agreement beats one high place.
  • d5 is first in one list and second in another, and still comes third. It is missing from list A, and a missing list gives zero points.
  • There are ties. d7 and d8 have the same score. A real system needs a fixed tie-break rule, or two runs of the same code can give different lists. Ours breaks ties by document ID.

What fusion cannot do

Fusion only re-orders what the searches found. If no list contains a document, fusion cannot add it. To find more, you need a different search or a deeper one, not a better fusion formula.

How we did it at TREC 2026

In the RAG track, each narrative is a long paragraph. We wrote seven versions of it as queries, such as the full narrative, its first sentence and two keyword versions (Chapter 7). No language model was used to write them. Each version went to BM25 on the ClimbMix corpus. RRF merged the seven lists, and the top 100 became the evidence pool for all our generation runs.

The two RAGTIME retrieval runs are a planned pair. They use the same ten lists and differ only in the fusion method. In the top 20 documents, the two methods agree on 74%. So the choice of fusion formula changes about a quarter of what a reader would see first.

What surprised us

Fusion bought coverage, not precision. The plain fused list has fewer relevant documents than the median run: set precision 0.2004 against 0.3499. Yet it covers more of the key facts: nugget gain 0.7139 against 0.6268. Seven different views of the question pull in documents on many sides of the topic, including many that are off target. For a RAG system that is often the right trade, because the writer needs every key fact once and does not need the same fact ten times. But we cannot say why the deep pool, which has more relevant documents, covers fewer nuggets. The data to test that has not been released.

A second lesson came from our own logs. In the first pool, each of the seven searches returned 100 documents. That made 28,256 different narrative-document pairs, but only the fused top 100 per narrative, 11,872 pairs, ever reached the reranker. Nothing below fused rank 100 could be rescued. Fusion followed by a hard cut can throw away documents that a better model would have liked.

Try it

Lab 3, part 1. RRF fits in ten lines of Python. Type it in, then check it against the worked example above.

from collections import defaultdict

def rrf(lists, k=60):
    """lists: several ranked lists of document ids, best first."""
    score = defaultdict(float)
    for one_list in lists:
        for rank, doc in enumerate(one_list, start=1):
            score[doc] += 1.0 / (k + rank)
    # highest score first; ties broken by document id
    return sorted(score.items(), key=lambda kv: (-kv[1], kv[0]))

A = ["d3", "d1", "d7", "d2"]
B = ["d1", "d5", "d3", "d9"]
C = ["d5", "d1", "d8", "d3"]
for doc, s in rrf([A, B, C]):
    print(doc, round(s, 4))
  1. Run it. Do you get d1, d3, d5 at the top with 0.0487, 0.0479 and 0.0325?
  2. Change k to 1. The order of this example stays the same, but look at the scores: first place is now worth much more than fourth. Build a small example where k = 1 and k = 60 give a different winner.
  3. Remove the tie-break (kv[0]) and explain why that is risky for a submission that must be reproducible.
  4. With an agent: ask a coding agent to write RRF without showing it this code. Then audit it. Does it start ranks at 0 or at 1? What does it do with ties and with duplicates inside one list?

Check yourself

  1. Why is it unsafe to add a BM25 score to a cosine similarity?
  2. With k = 60, which is worth more: one first place, or two places at rank 70?
  3. A document is ranked 1 by one search and is missing from six others. Where will it land after RRF over all seven, roughly?
  4. Your fused top 100 misses a document you know is relevant. Name two different reasons this can happen.
  5. Our fused list had lower precision but higher nugget gain than the median. What does each number measure, in plain words?
Answers
  1. They are on different scales. BM25 has no fixed range and cosine similarity stays between −1 and 1, so the larger numbers decide the sum.
  2. One first place, but only just: 1/61 = 0.0164 against 2 × 1/130 = 0.0154. That closeness is the point of a large k.
  3. It keeps only 1/61 = 0.0164. Any document that appears in two or more lists near the top will pass it, so it usually drops well down the list.
  4. No search returned it at all, or it was returned low in few lists and fell below the cut.
  5. Precision: the share of the returned documents that are relevant. Nugget gain: the share of the key facts that the returned documents contain.

Go deeper

  • Why 60? Cormack, Clarke and Büttcher chose k = 60 in a pilot study and reported that the result is not sensitive to the exact value. Treat it as a default, not a law. Test k on development data if you have any.
  • Score fusion. CombSUM adds normalized scores, and CombMNZ also multiplies by the number of lists that returned the document. Score fusion keeps the size of the gap between documents, which RRF throws away. It needs careful normalization, and one outlier score can squeeze all the others together. Our isu-mlir-csum run exists to test this against RRF on the same lists.
  • Weighted RRF. Multiply each list's points by a weight if you trust one search more. With labelled queries you can learn the weights.
  • Fusion and depth interact. Fusing lists of 100 and fusing lists of 1,000 give different top 100s. Our deep pool is the experiment for this. See Chapter 10.
  • Fusion of answers, not documents. In Video QA we fused the answers of several models. The problem is different, because the things being merged are a handful of options and not ranked documents. See Chapter 37.
  • Project idea. Take the seven-list pool for ten narratives. Compare RRF at k = 1, 10, 60 and 200 with CombSUM. Measure how much the top 20 changes, then judge by hand which version you would rather give to a writer.
