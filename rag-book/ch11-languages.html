Part 2 · Finding the evidence · Chapter 11

Many languages

In one sentence: when the question is in one language and the useful documents are in several, you must bring them together somewhere, by translating the question, translating the documents, or using a model that places all languages in one shared space.

Why you should care

Most of the world's text is not in English. A report on a flood, an election or a disease is better when it draws on what was written where the event happened. Search across languages is also a clean test of everything in Part 2, because keyword matching fails completely and you can see what each other method adds.

Words you need

Monolingual retrieval
The query and the documents are in the same language.
Cross-language retrieval (CLIR)
The query is in one language and the documents are in another.
Multilingual retrieval (MLIR)
The documents are in several languages, and the system returns one ranked list across all of them.
Query translation
Translate the query into each document language, then search in each language.
Document translation
Translate every document into the query language ahead of time, then search as usual.
Multilingual embedding model
An embedding model trained so that texts with the same meaning in different languages get nearby vectors.
Language bias
A system favouring documents in one language, often the language of the query, whatever their content.
Pipeline
Here: one search setup over one part of the collection, such as “Chinese documents only”.

Core The idea

An English query for “bridge repair” shares no word with a Chinese or Russian news story about a bridge repair. BM25 scores those stories zero. There are three ways around this.

ApproachHowStrengthWeakness
Translate the queryOne translated query for each language, then a search in each languageCheap. Nothing to do ahead of time.A short query is hard to translate well. One wrong word ruins the search.
Translate the documentsMachine-translate the whole collection once, then search in one languageFull sentences translate better than short queries. Any English tool then works.Costly for a large collection. Translation errors stay in the index.
Shared embedding spaceA multilingual model embeds queries and documents of every language into one spaceNo translation step at allNeeds a model that covers your languages well. Scores can favour some languages.

One list from several languages

If you search each language separately, you end with several ranked lists. Merging them is the fusion problem from Chapter 8, with one extra danger: scores from different language collections are not on the same scale. A score of 0.6 on the Spanish documents and 0.6 on the Chinese documents need not mean the same thing. Fusing by rank avoids comparing the scores. Fusing by score keeps more information and trusts that the scales match.

After retrieval

The writer has to read what the search found. Present-day language models read many languages, so a system can pass documents in their original language and ask for the report in English. The citations then point to sources the reader may not be able to read. That makes checking the support for each sentence harder (Chapter 19).

How we did it at TREC 2026

RAGTIME is the track where this chapter applies. A topic is a report request with a title, a problem statement and a description of the person asking. The documents are news in four languages. The report must be in English.

As in the RAG track, we did not hold the collection. The track runs a search service that uses Qwen3 embeddings, a shared embedding space. The service offers five pipelines: one over all the documents together, and one for each language.

Our base recipe uses no language model and no translation:

  1. Take two queries from the topic: the title and the problem statement.
  2. Send each query to all five pipelines. That gives ten ranked lists.
  3. Fuse the ten lists into one.
RunQueriesFusion
isu-mlir-baseTitle and problem statement, as writtenRRF, k = 60
isu-mlir-csumThe sameCombSUM on min-max normalized scores
isu-mlir-solAdds an English rewrite by a language model and queries in the other languagesLonger lists that contain every document of the base run

The first two runs are a clean pair: the same ten lists, a different fusion formula. They agree on 74% of the top 20 documents. The third run changes three things at once against the first: the rewritten English query, the query languages and the list length. It contains every document of the base run and adds more. Because three things changed together, a difference in score between the first and third run cannot be assigned to any one of them.

Why search the language pipelines separately when one pipeline covers everything? Our reasoning was about language bias. In a single list over all languages, documents in the query's language may crowd out the rest. A separate search for each language guarantees every language a list of its own, and fusion then decides how they mix.

The same ten-list retrieval fed our report runs. From the top 40 fused documents a language model selected 18 as truly responsive, and the writer received those 18 in full (Chapter 16).

The RAGTIME scores we have are preliminary and marked by the organizers as not for public use. They are not shown in this book. See Our TREC 2026 in five minutes.

What surprised us

Some topics had nothing to find, and the search did not say so. Two RAGTIME topics ask about the same music-recording fraud. We could find no document about it in the collection. The title query returned general articles about scams, with cosine scores near 0.28 to 0.30, very low for this search service. We then searched the full text of all 194 documents that any of our base queries had returned for one of the topics, and the names in the request did not appear once. Dense search always returns something. It never comes back empty the way a keyword search can. A system must notice from the scores that the evidence is missing, and the report must then say so instead of writing around it.

Try it

  1. Take ten sentences in English and translate five of them into another language you can read. Search all ten with BM25 using an English query. Which ones can it find?
  2. Repeat with a multilingual embedding model. Does the right sentence come first in both languages?
  3. Look at the scores. Are they higher, on average, for the sentences in the query's language?
  4. Search for something that is not in your ten sentences. What is the top score? Decide on a rule for “nothing found”.

Check yourself

  1. Why does BM25 fail across languages?
  2. Name the three ways to bridge languages, with one strength of each.
  3. Why is rank fusion a safe choice when merging lists from different language collections?
  4. Our first two retrieval runs differ in one thing. What is it, and why does that make them a useful pair?
  5. A dense search returns ten documents for a topic the collection does not cover. How might you notice?
Answers
  1. It matches words, and the same idea is written with different words in each language.
  2. Translate the query: cheap. Translate the documents: better translations, and any English tool works afterwards. Shared embedding space: no translation step.
  3. It uses positions only, so it never compares scores that may be on different scales.
  4. The fusion formula. Any difference in their scores can only come from the fusion.
  5. The top scores are unusually low, and the key names in the request do not appear in the returned text.

Go deeper

  • The evaluation line. Cross-language search has been evaluated at TREC, CLEF, NTCIR and FIRE for decades. TREC NeuCLIR tested neural methods on Chinese, Persian and Russian news, and RAGTIME continues that work with report generation.
  • Measuring language bias. Compare the share of each language among the judged relevant documents with its share in your top results. A large gap is bias.
  • Translation as training data. Many multilingual retrievers are trained on translated copies of English question-and-passage data. Their quality then depends on the translation quality for each language.
  • Sparse methods across languages. Learned sparse models and probabilistic translation tables can map query words to words in other languages while keeping an inverted index.
  • Mixed-language evidence in the writer. Does a language model use an English document more readily than a Russian one with the same facts? This can be tested by translating the evidence and comparing citations.
  • Project idea. Build the pair of runs from this chapter on a public multilingual collection, such as the NeuCLIR data. Add a third run that searches only the all-languages pipeline. Report the language mix of the top 20 for each run.
