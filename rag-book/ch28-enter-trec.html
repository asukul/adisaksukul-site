Part 5 · TREC and the 2026 tracks · Chapter 28

How to enter TREC with a student team

In one sentence: entering TREC means registering in spring, building in early summer, uploading valid runs before a fixed deadline, writing a paper in autumn and giving a talk in November, and most of what goes wrong is paperwork and logging, not modelling.

Why you should care

TREC is open to anyone, and it costs almost nothing to enter. A class project can become a scored run in the same table as large research labs (Chapter 23). The barrier is not skill. It is knowing the steps, the dates and the small traps. This chapter is the checklist we wish we had been given, written from one team's year.

Words you need

Evalbase
NIST's website for registering a team, uploading runs and uploading papers.
Dissemination agreement
A form an organization signs once a year. It sets the rules for how TREC results may be used and shared.
Run cap
The largest number of runs a team may send to one task.
Run description
The form you fill in with each upload: what the system does, which data and models it used, and its priority.
Validator
A program that checks a run file against the format rules.
Manifest
Your own list of every run you sent, with file name, date, and a fingerprint of the file.
Notebook paper
The paper each team writes before the workshop.
Checksum
A short fingerprint computed from a file. If the file changes, the fingerprint changes.

The year on one page

  1. 1RegisterCreate the team on Evalbase, choose tracks, and have your organization sign the agreement. Do it early. Nothing can be uploaded before it.spring
  2. 2ReadRead each track's guidelines to the end. Join the track's mailing list or chat.May, June
  3. 3Build on development dataGet one complete, valid run early, even a weak one. Then improve it.June, July
  4. 4Run on the test topicsFreeze the system. Run. Validate. Upload with a description and a priority.July to October
  5. 5WaitScores arrive by e-mail, track by track.autumn
  6. 6WriteUpload the notebook paper and sign the copyright form.early November
  7. 7PresentGive a talk or a poster at the workshop, in person or online.mid November

Three rules to know before you start

  • A submitted run cannot be withdrawn. Check before you upload, not after.
  • Every team that submits must write a paper. Plan the time for it.
  • Before the workshop, share only your own results. A preprint may contain the scores of your own system and nobody else's. Some tracks ask for more care still, and mark early scores as preliminary.

What to log, from the first day

  • For every run: the file, its checksum, the date, and the exact text you typed into the description form.
  • The prompts and instructions, the model names with versions, and every setting.
  • Every single verdict of every judge you run, not only the averages.
  • The costs: money, tokens and hours.
  • A dated note of what you decided and what you expected, written before the scores (Chapter 22).

What it costs

Entering is free. The data is free for participants. What you pay for is model calls and computing time, and your team decides how much. A team with open models and a university computer can enter for almost nothing.

What surprised us

Almost every problem was a process problem. Here is the list, so that you can skip it.
  • New data, old runs. The Video QA organizers released a corrected data file after we had uploaded five runs. With the new file, about half of each old run would have scored zero, with no error message. The notice came by e-mail, and the runs were redone. Read every message from the organizers on the day it arrives.
  • The wrong file had the right name. The file named exactly as the guidelines suggest was, in our folder, the weakest baseline. A manifest with checksums is what stops you from uploading it.
  • A validator that warns is not a validator that stops. The RAGTIME checker only warned about reports over the length limit unless a strict option was set. We had not set it.
  • What you type into a form is data. One run's description existed only in the text typed into the upload form, and that run was missing from our own list. Priorities typed as free text were later out of date. Save the form text with the run.
  • We did not keep what we could not rebuild. Judge verdicts, the instructions given to agents, and the exact model name in some outputs were not saved (Chapter 19).
  • Papers have their own route. One paper was first sent by e-mail and had to be uploaded to Evalbase instead. Another went in one day late. The upload page gave no receipt, so we recorded the file's checksum and the time ourselves.
  • Websites have quirks. One edit page returned an error, and one delete button did nothing. Leave a day for the upload itself.

And one thing went better than expected. Organizers answer. Every time we wrote with a clear question, about a late run, a data rule or a talk slot, a person replied.

Try it

  1. Choose one track from this year's TREC call. Write its timeline on one page: guidelines, test data, deadline, paper, workshop.
  2. List what your team would need for it: data, computing, models, people, hours per week.
  3. Write a manifest template: one line per run, with the columns you would need to rebuild that run a year later.
  4. Write the five-line plan from Chapter 22 for the two runs you would send first.
  5. Find the track's validator. Run it on a file you break on purpose. Does it stop, or only warn?

Check yourself

  1. What must be signed before a team can upload anything?
  2. Name two obligations a team accepts when it submits a run.
  3. Why should the first goal be one complete, valid run, even a weak one?
  4. Name four things to save for every run.
  5. Why is it risky to rely on a validator's warnings?
Answers
  1. The organization's dissemination agreement, once per year. Some tracks need a separate data agreement too.
  2. The run cannot be withdrawn, and the team must write a paper. Also: only its own results may be shared before the workshop.
  3. It proves the whole path works, from data to upload, while there is still time. Format and process problems appear early and not on the last night.
  4. Any four of: the file, its checksum, the date, the description text, the prompts, the model names and versions, the settings, the judge verdicts, the cost.
  5. A warning does not stop the upload, and nobody reads a long log at midnight. Make every rule a hard failure.

Go deeper

  • How many tracks? For a first year, one track with two tasks is plenty. Choose one with released baselines and development data, so that the first valid run takes days and not weeks.
  • Roles in a team. Give one person the rules and the calendar, one the validator and the manifest, and keep one away from the test data until upload. Rotate the roles each year.
  • The paper. Write the system description while you build, not in November. The notebook paper is not peer reviewed, and it is where your failed ideas can be recorded honestly.
  • Subscriptions and limits. Model subscriptions and free tiers are limited by time windows. A run that needs 100 hours of them cannot be started three days before a deadline.
  • Data rules as part of the method. Write down, per track, what may be looked at and by whom, including your coding agents (Chapter 26).
  • Project idea. Run a small TREC inside your class: one collection, twenty topics, a deadline, a validator, blind judging by another group, and a ten-minute talk from each team.
